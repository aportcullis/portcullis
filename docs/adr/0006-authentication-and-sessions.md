# ADR-0006: Authentication & sessions

- **Status:** Accepted
- **Date:** 2026-06-28

## Context
The MVP authenticates with local email/password and server-side sessions, and bootstraps the first
admin on a fresh install. This ADR fixes the session, cookie, and CSRF mechanics. It conforms to the
product requirement of HttpOnly/Secure/SameSite cookies, server-side opaque sessions with idle and
absolute expiry, rotation on login, and CSRF protection for state-changing requests; where the
web-verified standard is more specific, this ADR refines the requirement (and the PRD is amended to
match).

Standards verified on 2026-06-28 (OWASP):
- Session tokens should be opaque, generated by a CSPRNG, with high entropy (≥128 bits).
- Cookies should be `HttpOnly; Secure; SameSite`, ideally with the `__Host-` prefix.
- A new session id must be issued on login (session-fixation defense).
- Naive double-submit CSRF is bypassable; the token should be **HMAC-signed and session-bound**.

## Decision

### Session token & storage
- Token = **32 random bytes from `crypto/rand`** (256-bit), opaque (carries no user data).
- The store keeps only **`sha256(token)`** (column `sessions.token_hash`); the raw token lives only
  in the cookie. (The token is high-entropy, so an unkeyed hash is sufficient to prevent reversal.)
- `sessions` rows carry `idle_expires_at`, `absolute_expires_at`, `revoked_at`.

### Cookie
- Name **`__Host-portcullis_session`**; attributes **`HttpOnly; Secure; SameSite=Lax; Path=/`**, no
  `Domain`. The `__Host-` prefix forces Secure + Path=/ + no Domain (host-locked).
- `SameSite=Lax` (not Strict) so top-level navigations to the app keep the session; combined with the
  CSRF token below this is sufficient.

### Lifecycle
- **Rotation:** every successful login creates a **new** session (fixation defense); login/privilege
  change invalidates the prior session.
- **Expiry:** idle 12h, absolute 7d. `Authenticate` rejects revoked/idle-expired/absolute-expired
  sessions. Logout sets `revoked_at`.

### CSRF — HMAC, session-bound double-submit
- On login, issue a CSRF token = **HMAC-SHA-256(keyring payload-integrity key, session_id || nonce)**
  with the nonce suffixed, delivered in a readable cookie **`__Host-portcullis_csrf`**
  (`Secure; SameSite=Lax; Path=/`, **not** HttpOnly so the SPA can echo it).
- State-changing / authenticated RPCs must send the token in the **`X-CSRF-Token`** header; the
  server verifies the HMAC binds to the request's session **and** that header == cookie. This avoids
  the bypasses of naive (unsigned, unbound) double-submit.
- `Bootstrap` and `Login` are public (no session yet); `Logout`/`Me` and future mutations require it.

### Passwords & bootstrap
- Passwords use Argon2id via the crypto package (ADR-0003), with its validated parameters.
- **Bootstrap** creates the first admin (active user + `admin` membership in the default org) only
  when zero users exist; otherwise it is refused.

## Consequences
- `app/identity.AuthService` owns Login/Logout/Authenticate/Bootstrap; transport sets/clears the two
  `__Host-` cookies and runs a session+CSRF interceptor. The CSRF HMAC reuses the keyring, so no new
  key material is introduced.
- PRD §8.3 is amended to specify the `__Host-` prefix, `SameSite=Lax`, and the HMAC-bound
  double-submit CSRF token (it previously said only "CSRF token").
