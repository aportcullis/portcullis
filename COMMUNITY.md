# Portcullis community

Portcullis is an Apache-2.0 project in development alpha. We welcome users, documentation contributors, testers, designers, and developers. Start with the [quickstart](docs/operations/pg-alpha-quickstart.md), [product tour](docs/media/product-tour.md), or [contribution guide](CONTRIBUTING.md).

## Ways to participate

| Path | First step | Useful contribution |
| --- | --- | --- |
| Try the application | Run the PostgreSQL quickstart with disposable data | Describe what worked, where you got stuck, and the workflow you need |
| Make a first contribution | Find a maintainer-prepared `good first issue`, or ask for a small task | Improve documentation, reproduce a bug, or fix a bounded UI issue |
| Develop a feature | Discuss scope and acceptance criteria before implementation | Add a scenario-tested change aligned with the PRD and roadmap |
| Participate regularly | Help with reviews, issue triage, and onboarding | Build familiarity with an area and help its next contributor |

Using the product, reporting confusing behavior, translating documentation, and helping another user all count as participation. You do not need a development environment to share a use case or improve prose.

## Where conversations belong

GitHub is our initial home for community discussion and development records. Reddit and X help people discover the project; questions and decisions should return to GitHub so others can find them.

| Channel | Purpose |
| --- | --- |
| Discussions — Welcome | Introductions, how to get involved, and maintainer updates |
| Discussions — Q&A | Installation, usage, and troubleshooting questions; mark useful answers |
| Discussions — Ideas | Problems, proposed workflows, and feature exploration before scope is accepted |
| Discussions — Show and tell | Synthetic demos, experiments, and experience reports |
| Issues | Reproducible bugs and accepted, actionable work with completion criteria |
| Pull requests | Reviewable implementation, documentation, and validation |

**Rollout status:** This channel layout is decided, but remote Discussions activation and category setup have not been verified. Until it is live, use [GitHub issues](https://github.com/aportcullis/portcullis/issues) for questions and ideas too. The [launch checklist](docs/community/launch-checklist.md) records the setup work. An Ideas discussion is not a delivery commitment; accepted work becomes an issue.

A separate Slack or Discord and recurring meetings can follow when participants need real-time discussion and someone can maintain them. Important decisions still belong in GitHub and project documents.

## First-contribution issues

Maintainers use `help wanted` for useful, agreed, bounded work. Add `good first issue` only when all of the following are ready:

- A clear problem and observable completion criteria, with no unresolved product decision.
- Relevant files, examples, and background reading.
- Reproduction steps or a starting fixture, plus appropriate verification commands.
- A small scope that does not require advanced project knowledge.
- A named maintainer who will help with questions and review the first PR.

Both labels apply to a first-contribution issue. A draft with no reviewer is not ready for that label. Keep these issues current; remove the label when scope or prerequisites change.

Comment before starting an existing issue so a maintainer can confirm scope and avoid duplicate work. Ask for clarification when blocked. Maintainers should help contributors understand failing checks and identify a related next task after the first merge.

## Continuing participation

Regular contributors can help reproduce reports, review changes, maintain documentation, and mentor first-time contributors. Repository permissions and merge authority are separate from participation; they require an explicit maintainer decision. Contributions do not automatically confer write access. There is no numeric PR quota or automatic promotion rule.

Maintain a respectful, welcoming environment. Discuss behavior and evidence, explain review requests, and credit useful contributions in public change records. Share synthetic examples and redact private data. This page defines participation expectations; a formal Code of Conduct and its reporting contact remain launch setup work.

## References

The participation model follows [OPA's purpose-based contribution paths](https://www.openpolicyagent.org/docs/contributing), [Kubernetes first-issue preparation](https://www.kubernetes.dev/docs/guide/help-wanted/), [non-code participation](https://www.kubernetes.dev/docs/guide/non-code-contributions/), and [Prometheus's channel separation](https://prometheus.io/community/). References were checked on 2026-10-03; the choices above are Portcullis's own initial model.
